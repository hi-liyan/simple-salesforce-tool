# Query 工作区 WHERE / 排序输入体验优化设计

**日期**: 2026-04-24

**目标**: 优化 Query 工作区 `WHERE` 与“排序”输入框的企业级输入体验，解决“聚焦即全量提示”“回车无法直接查询”“长表达式显示不完整”三类问题，在不破坏现有多 Tab 草稿态与查询执行链路的前提下提升录入效率与可预期性。

## 背景

当前 Query 工作区的查询栏由 `DataQueryTabPane` 组合 `MysqlSmartInput` 与 `SalesforceSmartInput` 实现：

- 输入框聚焦时会立即打开候选面板。
- 候选来源由字段名、函数、关键字静态拼接组成。
- `Enter` 在输入框内部优先用于确认补全，无法直接触发查询。
- 输入框宽度依赖手动拖拽，长条件输入时容易被截断。

这套行为在功能上可用，但不符合企业级查询工具的高频输入场景：

- 用户只想继续录入时，聚焦即出现整屏候选会打断注意力。
- 用户习惯通过回车快速执行查询，但当前需要额外切换焦点或点击按钮。
- `WHERE` 与排序条件通常是长文本，固定宽度会增加校对成本与误操作风险。

## 已知约束

- 当前会话基于仓库内全量检索完成上下文收集，相关实现已覆盖：
  - `src/features/main/QueryPanel/components/DataQueryTabPane.tsx`
  - `src/features/main/QueryPanel/components/MysqlSmartInput.tsx`
  - `src/features/main/QueryPanel/components/SalesforceSmartInput.tsx`
- 现有 QueryBar 已使用本地草稿态 + 防抖回写 store 的模式，且通过 `bindingKey` 保证跨 Tab 精准写入。
- 本次改造必须保留 UTF-8（无 BOM）与 LF 约束，且新增或修改代码继续补充中文注释。
- 本次不引入新的重量级编辑器或语法引擎，不将单行输入框升级为 Monaco 等复杂组件。

## 用户已确认的交互边界

### 回车语义

- 当 `WHERE` / 排序输入框聚焦时，按下 `Enter` 应支持直接触发查询。
- 若候选面板已打开，只有“用户先通过上下方向键显式移动过候选高亮”时，`Enter` 才优先确认候选。
- 若候选面板已打开，但用户未显式选中过候选，则 `Enter` 仍直接查询。

### 宽度自适应

- 输入框宽度随内容变化实时伸缩。
- 当内容变短时，输入框也应自动收缩，而不是只增不减。
- 宽度增长到最大值后停止扩张，并通过输入框自身滚动保证内容可继续完整查看。

### 候选触发

- 输入框仅聚焦但尚未输入时，不自动弹出候选。
- 用户开始输入后，按当前输入内容进行关联提示。
- 保留 `Ctrl+Space` 手动唤起候选的能力，即使当前输入为空也允许打开。

## 范围

本次纳入范围：

- Query 工作区查询栏中的 `WHERE` 输入框
- Query 工作区查询栏中的“排序”输入框
- MySQL / Salesforce 两套 SmartInput 的候选触发、键盘行为、宽度策略
- `Enter` 触发 QueryBar 统一查询动作
- 输入候选排序与候选呈现的轻量优化
- 相关可测试 helper 与测试补充

本次不纳入范围：

- `LIMIT` 输入框交互重做
- SOQL / SQL 主编辑器 (`SoqlMonacoEditor`) 行为调整
- Query 结果执行链路、保存链路、持久化快照结构调整
- 引入完整语法感知补全系统
- 新增后端接口或修改 API 数据结构

## 方案选择

本次采用“增强现有 SmartInput 组件”的方案。

### 选择原因

- 现有交互问题集中在输入组件层与 QueryBar 调用层，改动点清晰。
- QueryBar 现有草稿态、防抖回写与跨 Tab 绑定逻辑已经较稳定，不宜为一次交互优化进行架构级重写。
- 在现有组件上做增强，能以最小改动面获得最直接的体验提升。

### 不选方案

不选择“抽象全新通用 `QuerySmartInput`”：

- 会扩大改动面，增加本轮回归成本。
- 当前核心目标是交互修正，不是组件体系重构。

不选择“做强语法感知补全”：

- 实现与测试复杂度明显偏高。
- 本轮需求没有要求解析完整语义树，超出必要范围。

## 总体设计

### 一、保留 QueryBar 为查询动作唯一入口

`DataQueryTabPane` 中的 `QueryBar` 继续作为：

- `WHERE` / 排序 / `LIMIT` 草稿态的宿主
- 执行查询前统一提交草稿并调用 `onQuery` 的唯一入口

本次不让 SmartInput 直接执行业务查询，而是通过参数把“回车触发查询”回调传入输入组件，保持职责边界稳定：

- SmartInput 负责识别当前键盘意图
- QueryBar 负责真正执行查询

### 二、候选从“聚焦即展示”改为“输入驱动 + 手动唤起”

候选面板展示策略调整为：

- 仅聚焦时不展示候选
- 用户输入后，根据当前光标所在 token 计算候选并展示
- `Ctrl+Space` 可强制打开候选
- 候选为空时不展示空面板

这可以把提示行为从“系统主动打断”改为“用户正在录入时的即时辅助”。

### 三、回车从“默认补全”改为“默认查询”

键盘行为调整为：

- `Enter`
  - 若用户已通过方向键显式移动高亮，则确认当前候选
  - 否则触发查询
- `Tab`
  - 始终作为补全确认键
- `ArrowDown` / `ArrowUp`
  - 在候选打开且有数据时移动高亮
  - 一旦发生移动，记录“用户已显式选择候选”
- `Escape`
  - 仅关闭候选面板

此策略兼顾两类用户：

- 高频回车执行查询的用户
- 依赖键盘补全的高级用户

### 四、宽度改为内容驱动的自适应策略

输入框宽度不再依赖手动拖拽把手，而是使用内容测量结果实时驱动：

- 以当前输入值为主计算宽度
- 空值时参考 placeholder 与默认宽度，避免输入框过窄
- 保留最小宽度与最大宽度
- 达到最大宽度后停止扩展，但输入框内部继续水平滚动

这样既能保证长表达式尽可能完整显示，也能避免把查询栏其余控件挤出工作区。

## 详细交互设计

### 候选触发规则

#### 默认触发

- `onFocus`
  - 仅同步光标位置
  - 不自动打开候选
- `onChange`
  - 更新输入值
  - 重新计算当前 token
  - 若输入非空或当前为手动唤起模式，则根据候选结果决定是否打开面板

#### 手动触发

- `Ctrl+Space`
  - 强制打开候选面板
  - 若当前 token 为空，则展示去重后的前置候选集
  - 若候选为空，则不展示面板

#### 关闭时机

- 点击组件外部区域
- `Escape`
- 鼠标点选候选并完成替换
- 查询执行完成前，输入组件本身不强制清空候选状态；是否关闭由输入组件在执行查询前自行收起

### 候选排序策略

保留“前缀优先、包含次之”的基本规则，并增加业务优先级：

- 字段名优先于关键字与函数
- 排序输入中，若当前 token 更接近排序方向语义，则优先 `ASC` / `DESC`
- 去重规则继续保持大小写不敏感

第一版不做复杂分组 UI，但允许在候选项渲染中预留轻量标签能力，便于后续扩展字段 / 函数 / 关键字区分。

### 键盘行为状态机

输入组件新增一个轻量状态，例如：

- `hasExplicitSelection`

语义如下：

- 初次打开候选时为 `false`
- 用户通过 `ArrowUp` / `ArrowDown` 移动高亮后置为 `true`
- 候选列表变化、输入变化、关闭面板后重置为 `false`

据此定义 `Enter` 语义：

- `open = true` 且 `filteredSuggestions.length > 0` 且 `hasExplicitSelection = true`
  - 应用当前候选
- 其他情况
  - 调用 QueryBar 传入的 `onSubmit`

### 查询触发

`WHERE` 与“排序”输入框都接入同一个 `onSubmit` 回调，回调落到现有 `handleQueryClick`：

- 先清理防抖计时器
- 再提交 `whereDraft` / `sortDraft` / `limitDraft`
- 最后调用 `onQuery`

因此回车触发查询与点击“查询”按钮保持完全一致的业务结果。

### 宽度测量规则

建议为输入组件增加隐藏测量节点，使用与真实输入框一致的字体、字号、字重与内边距基准。

宽度计算建议顺序：

1. 先测量当前文本或 placeholder 的文本宽度
2. 再加上输入框左右 padding
3. 若启用清空按钮，再加上清空按钮预留宽度
4. 最后附加少量安全冗余，避免字符贴边

最终宽度取：

- `clamp(minWidth, computedWidth, maxWidth)`

空值时：

- 取 placeholder 宽度与默认宽度中的较大值作为测量基线

### 布局策略

- 查询栏保持单行横向布局
- 当窗口宽度不足时，外层容器维持横向滚动能力
- 自适应宽度只影响 `WHERE` 与“排序”输入框，不改变 `LIMIT` 与“查询”按钮尺寸策略

## 实现边界

### 建议新增的轻量 helper

建议把与 UI 框架无关的逻辑抽为可测试函数，例如：

- `filterSmartInputSuggestions(...)`
- `shouldOpenSuggestions(...)`
- `resolveEnterBehavior(...)`
- `measureSmartInputWidth(...)`

其中：

- token 解析逻辑可继续保留现有 `getTokenRange`
- MySQL 与 Salesforce 只需传入不同的 token 规则与候选集合

### 组件改造建议

#### `MysqlSmartInput`

- 移除“聚焦即打开候选”
- 接入 `onSubmit`
- 新增显式选择状态
- 移除手动拖拽宽度逻辑
- 增加基于内容测量的宽度状态

#### `SalesforceSmartInput`

- 与 `MysqlSmartInput` 同步收敛行为
- 保持现有适配 Salesforce token 的能力

#### `DataQueryTabPane / QueryBar`

- 将 `handleQueryClick` 作为 `onSubmit` 传给两类 SmartInput
- 不改动 `commitWhereClause` / `commitSortClause` / `commitLimit` 与防抖策略

## 测试设计

本次必须采用“先补测试，再改实现”的方式推进。

### 建议测试层次

#### 纯逻辑测试

在 `tests/query-panel/` 下新增针对 helper 的测试，覆盖：

- 候选过滤与排序
- `Enter` 行为判定
- 候选打开条件
- 宽度计算的上下限规则

#### 组件行为回归

若当前测试基础允许，可增加轻量行为测试；若不适合做 DOM 级测试，则至少保证关键逻辑沉淀为纯函数并测试。

### 必测场景

#### 候选触发

- 仅聚焦时不应自动打开候选
- 输入后应基于 token 过滤候选
- `Ctrl+Space` 可在空输入时手动打开候选
- 候选为空时不应显示空面板

#### 回车语义

- 面板关闭时，`Enter` 直接查询
- 面板打开但未显式选中过候选时，`Enter` 仍直接查询
- 面板打开且已通过方向键选中过候选时，`Enter` 应确认候选
- `Tab` 应继续确认候选

#### 宽度策略

- 内容变长时宽度增大
- 内容变短时宽度缩小
- 超过最大值后不再扩展
- 空值时不应缩到小于默认可用宽度

#### 回归验证

- 查询前草稿提交逻辑不变
- 切换对象 Tab 时草稿回写逻辑不变
- `WHERE` 与排序输入回车触发的查询参数与点击按钮一致

## 风险与缓解

### 风险一：`Enter` 行为改变导致补全用户不适应

缓解：

- 保留 `Tab` 补全
- 保留“显式方向键选择后 `Enter` 可补全”的能力
- 后续如有需要，可加轻量键盘提示文案

### 风险二：宽度测量不准确导致抖动

缓解：

- 使用隐藏测量节点而不是字符数估算
- 与真实输入框保持相同字体样式
- 增加最小宽度与安全冗余

### 风险三：QueryBar 频繁重渲染

缓解：

- 宽度状态保持在输入组件内部
- 不把宽度写入 store
- 不改动 QueryBar 现有草稿态与防抖回写边界

### 风险四：MySQL 与 Salesforce 输入行为再次分叉

缓解：

- 优先抽取共享 helper
- 两个输入组件只保留 token 规则差异

## 验收标准

满足以下条件即可视为本次体验优化完成：

1. `WHERE` 与“排序”输入框在仅聚焦时不自动弹候选。
2. 用户输入后，候选基于当前输入内容进行关联提示。
3. `Ctrl+Space` 可手动唤起候选。
4. 在 `WHERE` / “排序”输入框聚焦时，`Enter` 可触发查询。
5. 若用户已用方向键显式选择候选，则 `Enter` 优先补全。
6. 输入框宽度随内容实时扩张与收缩，并受最大宽度保护。
7. 达到最大宽度后，长表达式仍可在输入框内完整查看与编辑。
8. 现有 QueryBar 草稿态、防抖回写、跨 Tab 精准写入与查询执行链路无回归。

## 实施顺序建议

1. 先提炼并补齐 SmartInput 相关纯逻辑测试。
2. 再改造 `MysqlSmartInput` 与 `SalesforceSmartInput`。
3. 最后在 `QueryBar` 层接入 `onSubmit` 并做整体回归。

这样可以先锁定交互语义，再处理 UI 细节，降低实现阶段的返工概率。
